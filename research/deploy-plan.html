F1nsight в облаке за $0

Практический план для karroge10/F1nsight. Основан на локальном коде v2, фактических размерах файлов и проверенных страницах поставщиков. Домашний компьютер после первоначального переноса не участвует ни в обновлении, ни в обучении, ни в live.

Рекомендация: статический Next.js на Cloudflare Pages, обновление и прогноз на CPU в GitHub Actions, версионированное состояние в R2, FastAPI live и повторы на Oracle Always Free ARM. Обучение тоже переносится в облако, но полный retrain-gate нужно разбить на возобновляемые задания. Бесплатная архитектура возможна, гарантировать постоянную доступность live за $0 нельзя.

Существующее расписание: pipeline/src/f1p/weekend.py рассчитывает обновления через 60 минут после номинального конца, для гонки через 75 минут, повтор ещё через 3 часа, RaceMorning за 3 часа до старта. scripts/schedule-weekend.ps1 добавляет понедельник 10:00 локального времени. Текущий retrain-gate является одноразовой проверкой завершения bulk с повторами каждые 6 часов на 14 дней, а не готовым постоянным послегоночным расписанием.

Минимум для сайта

Для сборки безопасно передать весь data/serve и data/predictions, около 155 МБ, плюс код и public-assets. На выходе публиковать только HTML/JS/CSS, изображения и JSON, которые нужны клиенту. Не отдавать SQLite, raw, processed, модели, личные токены или служебные логи. Проверить точные JSON-зависимости экспортированного сайта до сокращения входа.

Минимум для надёжного incremental refresh

Начальный пакет: raw без больших вычислительных кэшей, processed, serve, predictions, data/manual, models, logs/refresh_state.json, gate-отчёт и результаты базового бэктеста. Некоторые ML-модули читают raw/f1db и raw/fantasy. Общий ориентир без FastF1-кэша: 1,86–1,90 ГБ. Сначала перенести этот пакет, провести два последовательных запуска на чистых runners и только после доказанного восстановления исключать источники. Не сохранять refresh.lock и PID-файлы между машинами.

Версии без потери целостности

Закрытый R2 Standard: snapshots/<id>/ с манифестом SHA-256, версиями схемы, модели, датами успешных источников и code SHA. Загружать данные новой версии, проверять их, затем переключать маленький current.json. Читатель выбирает один снимок на весь запуск. Хранить текущий и предыдущий пакеты, ориентир около 3,8 ГБ, ещё до 2 ГБ на ограниченные кэши и артефакты. Внутренний потолок 7 ГБ; при превышении останавливать публикацию и чистить только неприкреплённые старые версии. Сжатие полезно, но не включено в расчёт.

Конкурентность одного GitHub workflow не защищает от другого workflow, ручного скрипта или Oracle. Все writer-workflows должны использовать общую concurrency-group; при внешнем writer нужен распределённый lock с TTL либо единый диспетчер. Во время gate не удерживать блокировку refresh часами: кандидат работает с закреплённым snapshot, promotion заново проверяет актуальность базы.

4. Компоненты: размещение, ограничения и риски

Сайт: Cloudflare Pages, статический export

Сборка проходит в Actions, публикация через Wrangler Direct Upload. Pages Free: 500 сборок в месяц, 20 000 файлов, 25 MiB на asset; встроенная сборка ограничена 20 минутами. Планировать менее 100 публикаций в месяц, независимо от того, как Direct Upload учитывается в конкретном аккаунте. Перед deploy считать файлы и максимальный размер. Лимиты Pages.

Публиковать после изменения данных, модели или кода, а не после каждого пустого refresh. Статические страницы получают свежие данные только после следующей успешной сборки. Клиент проверяет время сессии самостоятельно: server-generated «сессия закончилась» устаревает между деплоями. Альтернатива: Workers Static Assets, если число файлов превысит Pages; прежде проверить актуальные лимиты Workers. Сохранять last-good deployment и free hostname f1nsight.pages.dev, если имя доступно.

Почему не OpenNext по умолчанию

OpenNext официально поддерживает Next.js 16, SSR, route handlers и ISR на Workers. Это полноценная альтернатива статическому export, а не устаревший next-on-pages. Однако Node API в Workers поддерживаются частично: наличие имени модуля не означает работоспособность. node:sqlite отмечен как stub, перенос нынешнего DatabaseSync не решается флагом совместимости. node:fs тоже не означает доступ к постоянному диску со свежими файлами R2. OpenNext, Node API Workers, Флаги и SQLite stub.

SSR-вариант требует нового async data adapter: D1 для SQL, R2/JSON для документов, bindings и согласованных версий. Workers Free: 100 000 вызовов в сутки, 10 мс CPU на вызов по странице pricing. Даже небольшой SSR может упереться в CPU при всплеске посещений. Проверять реальный worker-build и preview, измерять CPU; не считать бесплатное SSR гарантированным. Workers pricing. Для этого проекта данные пакетные, поэтому export проще контролировать по цене и устойчивости.

Хранилище: закрытый R2 Standard

Бесплатно в месяц: 10 GB-month хранения, 1 млн операций Class A, 10 млн Class B, egress без платы. Free tier не распространяется на Infrequent Access. Превышение платное: Standard $0,015/GB-month, Class A $4,50/млн, Class B $0,36/млн. R2 не является автоматически жёстко ограниченным бесплатным бакетом. R2 pricing.

40 запусков × 15 000 объектов дают около 600 000 чтений, далеко от Class B. Загружать только изменённые объекты либо несколько пакетов по источникам; бессмысленно копировать тысячи неизменных файлов в каждую версию. Lifecycle и лимит retained snapshots обязательны. Публичную телеметрию отдавать из Pages, чтобы посетители не создавали операции R2. Альтернатива: объектное хранилище Oracle, но это связывает резервную копию и live с одним аккаунтом. GitHub artifacts годятся для небольших логов, не как долговременная база.

Refresh и predict: GitHub Actions в публичном репозитории

Стандартные Linux runners публичного repo бесплатны: 4 vCPU, 16 ГБ RAM, 14 ГБ SSD по документации. Одна hosted job не дольше 6 часов. Не использовать larger runners, GPU runners и self-hosted на домашнем ПК. Внутренний timeout refresh 120 минут, retrain-shard 300 минут. Большой кэш 22,5 ГБ не помещается в заявленный SSD. CPU torch, ограниченный FastF1-кэш и поэтапная очистка оставляют место для Node build. Ресурсы runner, Лимиты Actions.

Jolpica обновляет историю; OpenF1 401 во время live у несponsors обрабатывать как временную недоступность, а не пустой набор данных. В refresh уже каждый шаг пробуется даже после ошибки другого. Публикация должна проверять полноту, а не только код завершения: не заменять успешные данные пустыми, сохранять дату источника, повторять после сессии. Fantasy зависит от доступности новых inputs. FIA PDF может появиться позже запланированного RaceMorning, сохранить retry и отдельно показывать актуальность штрафов. 429: backoff, ограничение запросов, повтор в следующем окне.

Предсказание запускать по fingerprint изменённых inputs, как уже делает refresh. Обеспечить стабильные hash после переноса файлов: восстановление снимка меняет mtime и может вызвать лишние rebuild/predict. CPU оставить 20 000 симуляций в production; снижение числа запусков допустимо только в диагностике. Альтернатива: Python на Oracle, но тогда нужны CPU/RAM isolation от live и больше зависимость от VM.

Retrain: отдельный возобновляемый Actions pipeline

Домашний GPU не нужен. Начать с текущей модели в R2, запускать candidate train после поступления окончательных результатов и полноты FastF1. Не запускать прежнюю одноразовую проверку bulk каждые 6 часов бесконечно. Новый gate сохраняет data snapshot, params и seed. Полный walk-forward разбивается по сезонам или детерминированным диапазонам с checkpoint моделей. Границы должны сохранить исходную семантику переобучения каждые три гонки, иначе показатели уже несопоставимы.

Aggregation проверяет ожидаемое число гонок и стадий, непустое пересечение baseline/candidate и исходные три критерия: post-qualifying log loss, post-qualifying Spearman, pre-weekend log loss. Сейчас отсутствие baseline разрешает promotion, а пустые метрики могут дать нули. В облаке при недостаточной проверке promotion запрещать. Не принимать решение по частичному smoke backtest. Публиковать модель и новые прогнозы атомарно, хранить предыдущую версию. Альтернатива при слишком долгом gate: те же возобновляемые задания на Oracle вне окон live, старую модель продолжать использовать до завершения.

Live: Oracle Always Free ARM

На проверенной странице Oracle: 1 500 OCPU-hours и 9 000 GB-hours в месяц, эквивалент 2 OCPU / 12 ГБ; 200 ГБ boot+block volumes, до пяти backups. VM создавать в home region с маркировкой Always Free. Начальная конфигурация: одна A1, 2 OCPU / 12 ГБ, boot 50 ГБ, Ubuntu ARM64. 31 день даёт 1 488 OCPU-hours и 8 928 GB-hours, поэтому второй ARM-инстанс уже может выйти за квоту. Oracle Always Free.

systemd держит uv run python -m f1live --host 127.0.0.1 --port 8765; Caddy принимает 443 и проксирует HTTP/WebSocket. Port 8765 закрыт снаружи, SSH только ключом, 80/443 разрешены в OS и OCI security rules. Один uvicorn worker сохраняет общий LiveHub и recording cache, несколько процессов удвоят upstream и RAM. Проверить ARM64 wheels FastF1, numpy и scipy. ML на эту VM по умолчанию не устанавливать.

Idle reclamation возможен, когда за 7 дней все критерии низкой загрузки соблюдены, в том числе CPU 95-й перцентиль ниже 20% и RAM ниже 20% для A1. Race weekend не гарантирует защиту в межсезонье. Не создавать искусственную нагрузку ради обхода. Сохранять конфигурацию и малые полезные reference-cache в R2; при reclaim сайт продолжает работать. Ошибка out-of-host-capacity и проверка карты могут вообще не дать получить VM. Переход на PAYG не считать доказанным способом отменить reclaim или безопасно увеличить бесплатный размер: сначала проверить условия именно аккаунта.

Повторы: на Oracle, по запросу

Архив скачивается с F1 static, разобранная запись разделяется через RecordingCache, размер LRU в коде 3. Но каждый ReplayPlayer имеет собственный SessionEngine, seek и часы, поэтому RAM/CPU растут с клиентами. Ограничить число активных replay-клиентов, размер записи и скорость; очередь с сообщением о лимите лучше OOM всей VM. Поставить TTL/размер дискового archive-cache, например 10 ГБ, и лимит RSS, который уточняется нагрузочным тестом.

Для доступности повторов процесс нужен круглосуточно, даже когда нет live-сессии. Предварительно прогреть один популярный replay, не скачивать все сезоны. Альтернатива без VM: заранее сформированные чанки replay в Pages и плеер в браузере. Это отдельная переделка protocol/seek и объёма файлов, поэтому не обещать её как бесплатную мгновенную замену.

Расписание: календарь + проверка просроченных задач

GitHub schedule выполняется на default branch, может задерживаться или терять задания при нагрузке; избегать нулевой минуты. В публичном repo расписание отключается после 60 дней без активности. Cron не годится для точного старта live. Правила schedule.

Каждый час в минуту 17 лёгкий planner получает маленький calendar/manifest из R2, вычисляет due-tasks через weekend.py и запускает тяжёлые шаги лишь при необходимости. Фактически это до 744 коротких проверок в месяц, но не 744 обновления и не 744 деплоя. При задержке догоняет задачи по UTC и сохраняет id выполненных задач; retry имеет собственный id. Еженедельный fallback перенести на понедельник 06:17 UTC, близко к 10:00 Asia/Tbilisi. RaceMorning оставить за три часа до старта.

Резервный systemd timer на Oracle раз в час делает workflow_dispatch через минимальный GitHub token, если expected run просрочен. Он тоже может отказать вместе с VM. Независимая альтернатива: маленький Cloudflare Cron Worker, который только читает manifest и вызывает GitHub API, не выполняет Python. Проверить его текущий CPU-limit в dashboard: страницы limits и pricing дают неоднородные значения для cron. Dispatch не гарантирует время старта runner, нужен deduplication. Не писать автоматические фиктивные коммиты ради сохранения schedule.

Телеметрия: готовые JSON в Pages

Существующие 323 файла экспортированы до переноса. f1p.fastf1.telemetry_export работает преимущественно offline по local cache, отсутствующие car data пропускаются. Он не создаст новые данные из одного raw/fastf1. Для свежей телеметрии нужен отдельный online loader с telemetry=True только для новой завершённой сессии, затем экспорт и обновление index.json. Скачивание и экспорт выполнять в Actions после FastF1 availability, хранить кэш только ограниченное окно. Сайт загружает выбранную сессию из статического URL, а не 46 МБ сразу. Альтернатива R2 public+CDN нужна только после роста: появляется учёт чтений и CORS.

7. Схемы workflows и согласованная публикация

Ниже проектные YAML-схемы, не готовые файлы. Обозначенные Python-скрипты ещё нужно реализовать. Пути workflows зависят от корня публичного repo: локальная папка v2 не доказывает, что в GitHub проект имеет тот же префикс. Перед реализацией проверить дерево karroge10/F1nsight. Версии Actions закрепить на проверенные commit SHA.

name: refresh
on:
  workflow_dispatch:
  schedule:
    - cron: '17 * * * *'
permissions:
  contents: read
concurrency:
  group: f1nsight-state-writer
  cancel-in-progress: false
jobs:
  refresh:
    runs-on: ubuntu-24.04
    timeout-minutes: 120
    env:
      F1ML_DEVICE: cpu
      OMP_NUM_THREADS: '4'
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - uses: actions/setup-node@v4
        with:
          node-version: '24'
      - run: python scripts/cloud-schedule.py --check-due
      - run: python scripts/cloud-state.py pull --snapshot current
      - run: python scripts/cloud-refresh.py --cpu --due-only
      - run: python scripts/cloud-state.py validate
      - run: python scripts/cloud-state.py stage
      - run: python scripts/cloud-refresh.py --build-and-deploy-if-changed
      - run: python scripts/cloud-state.py publish-manifest

Реальный YAML добавляет outputs planner и if: к тяжёлым шагам, setup uv, установку project dependencies и CPU torch, секреты через env, capture peak RSS/time и summary. Обычный запуск из pipeline/: uv run python -m f1p.refresh. Windows wrapper не требуется. Сохранить выполняемые им полезные image scripts после refresh, но не регистрацию Windows-задач. Установка Node 24 даёт необходимый node:sqlite для build.

name: retrain
on:
  workflow_dispatch:
jobs:
  candidate:
    runs-on: ubuntu-24.04
    timeout-minutes: 60
    steps:
      - run: python scripts/cloud-retrain.py candidate --snapshot SNAPSHOT_ID
  backtest:
    needs: candidate
    strategy:
      max-parallel: 2
      matrix:
        season: [2024, 2025, 2026]
    runs-on: ubuntu-24.04
    timeout-minutes: 300
    steps:
      - run: python scripts/cloud-retrain.py backtest --season ${{ matrix.season }} --resume
  promote:
    needs: backtest
    concurrency:
      group: f1nsight-state-writer
      cancel-in-progress: false
    runs-on: ubuntu-24.04
    timeout-minutes: 90
    steps:
      - run: python scripts/cloud-retrain.py aggregate-and-gate
      - run: python scripts/cloud-retrain.py promote-if-current

Каждый job дополнительно делает checkout, setup и восстановление закреплённого snapshot. Сезонный shard может не успеть за 300 минут, тогда делить его на диапазоны с checkpoint. Потерянные shards повторяются; promotion возможен только после всех. Нельзя прямо передать --season существующему backtest и считать семантику сохранённой без проверки перехода между сезонами и состояния trained.

Build trigger после обновления

  1. Восстановить snapshot N, выполнить refresh в рабочей копии, проверить SQLite integrity, обязательные таблицы, JSON schema и полноту свежих данных.
  2. Загрузить immutable snapshot N+1 и манифест candidate, не переключать current до валидации. Сохранить checkpoint успешных источников отдельно при частичной ошибке, не публиковать его как согласованный production snapshot.
  3. В той же writer-цепочке собрать сайт ровно из N+1, выполнить typecheck, export и smoke checks. Опубликовать Direct Upload через npx wrangler pages deploy out --project-name f1nsight.
  4. Проверить URL production и data-version, затем переключить production-manifest. Если deploy не прошёл, оставить прежний сайт/current, следующий запуск может повторно собрать N+1 без новых downloads.

R2 pointer и Pages deployment нельзя переключить общей транзакцией. Встроить snapshot-id в сайт, хранить отдельные data-current и site-current, а их несовпадение наблюдать и исправлять повтором. Для независимого site.yml использовать workflow_call или dispatch с конкретным snapshot-id. Не запускать новый build от случайного current. Пустой refresh не вызывает deploy; ручной deploy умеет выбрать предыдущий snapshot.

Фаза 0. Аккаунты и исходный снимок

  1. Владелец подтверждает публичность karroge10/F1nsight и право публикации данных. Проверяет корень repo и отсутствие токенов в текущих файлах. Создаёт Cloudflare account, Pages Direct Upload project и закрытый R2 Standard bucket; R2 может потребовать billing profile/карту.

  3. Однократно переносит текущие serve/predictions, raw без большого cache, processed, manual, models и baseline/gate-отчёты. Проверяет checksum и восстановление на чистой машине. Домашний компьютер нужен для этой начальной выгрузки, после неё отключается.

Контроль: нужный ARM shape реально получен, оценка стоимости $0, восстановленный SQLite проходит integrity_check, модели и baseline присутствуют. Если Oracle недоступен, продолжить сайт и pipeline, но зафиксировать, что обязательный live ещё не обеспечен.

Фаза 1. CPU и Linux без публикации

  2. Запустить два incremental refresh подряд. Второй не должен стирать историю, получать пустые источники или выполнять дорогой predict только из-за изменённого mtime.
  3. Проверить отложенную доступность OpenF1/FastF1, штрафы и корректность прогноза; измерить время и ресурсы. Секреты не выводятся в логах.

Собственный домен платный, но можно использовать уже имеющийся; Cloudflare DNS и TLS не требуют отдельной покупки домена у Cloudflare.
  3. Тестировать replay, pause, seek, speed и reconnect. Прогнать --simulate 2026:16:R --sim-anonymous для estimator, затем настоящую сессию. Simulation не заменяет проверку upstream в реальном времени.
  4. Нагрузочный тест и перезапуск VM. Настроить лимиты клиентов, проверить происхождение WS и отсутствие личных credentials в ответах.

Контроль: replay доступен вне сессий; live работает с домашним ПК off; process restart восстанавливает сервис; повтор не вызывает OOM.

Фаза 4. Автоматизация и обучение

  1. Подключить due-task planner с UTC, hourly cron, backup dispatch и weekly fallback. Проверить пропущенный run и deduplication.
  2. Реализовать checkpoint backtest, прогнать candidate/gate без promotion, подтвердить соответствие модели и параметров. Затем разрешить атомарный promotion только при полном сравнении.
  3. Проверить свежую telemetry export, автоматический build после изменённых данных и восстановление после failed deploy.

Контроль: минимум один полный гоночный уикенд и послегоночное облачное обучение проходят без ПК. Старую Windows-автоматизацию владелец отключает вручную только после приёмки, чтобы не было двух writers.

Фаза 5. Откат и восстановление

Если новый сайт плохой, вернуть предыдущий Pages deployment и site-current. Если новые данные повреждены, выбрать прошлый immutable R2 snapshot и пересобрать сайт; не пытаться исправить опубликованные объекты на месте. Если модель ухудшилась, вернуть предыдущий models/latest и весь связанный snapshot, повторить predict. При потере Oracle восстановить новую VM из описанной конфигурации и R2, перепривязать DNS; сайт показывает недоступность live до восстановления. При невозможности получить free VM решение владельца: временно отключить live или перейти на явно платный хост. Домашний ПК не использовать как скрытый fallback.

10. Наблюдение, уведомления и условия $0

  • GitHub: включить email/web notifications failed workflows. Job summary содержит snapshot-id, модель, успешность каждого источника, возраст данных, wall time, RSS и R2 total. Логи маленькие, artifacts на 7 дней; большие данные только R2.
  • Freshness: отдельный короткий health workflow проверяет Pages data-version, expected due-tasks, возраст прогноза и Oracle /health. /health сейчас подтверждает лишь живой процесс, поэтому дополнительно /status и возраст последнего upstream heartbeat. При ожидаемой активной сессии stale feed должен давать отдельную ошибку.
  • Независимость: GitHub monitor не обнаружит своё отключённое schedule. Резервный timer Oracle проверяет last-success и dispatch; владелец также подписывается на предупреждения аккаунтов. Если нужна независимая внешняя проверка, добавить доступный free HTTP monitor после проверки его актуального тарифа; не рассчитывать, что ping предотвращает reclaim Oracle.
  • Квоты: алерты R2 6 и 7 ГБ, отчёт Class A/B; pre-deploy caps файлов Pages; free compute/volume usage в OCI, rotation logs и предупреждение заполнения диска. Budget alerts уведомляют, но не являются гарантированным запретом списаний.
  • Сбой источника: 401/429 отражается в freshness и retries; fallback не подменяет отсутствующее новое событие ложным нулём. Отдельно проверять актуальность FIA penalties перед стартом.

11. Что должен решить владелец

  1. Приемлема ли возможная недоступность live из-за Oracle при сохранении сайта? Если требуется гарантия, понадобится бюджет и резервный хост.
  2. Готов ли владелец пройти Oracle card verification и включить R2 billing profile? Нужен ли строгий режим остановки до платного превышения?
  3. Выбираем static export с перечисленной переделкой UI или более быстрый временный Node deployment на VM? OpenNext требует отдельной data-layer миграции и CPU-проверки.
  4. Какие архивные сезоны и routes обязательны в первой версии? Это влияет на build time и Pages file count.
  5. Нужна ли свежая телеметрия после каждой сессии или достаточно race/qualifying? Это влияет на downloads и transient cache.
  6. Какой срок обновления считается достаточным: около часа после появления источников или быстрее? Бесплатные GitHub cron/источники точности не гарантируют.
  7. Оставляем полный walk-forward gate и его критерии? Нужно подтвердить, что он действительно обосновывает promotion именно производственной модели, и выбрать минимальную coverage.
  8. Нужен ли постоянный pre-session upstream без зрителей или достаточно существующего lazy subscribe? Это влияет на прогрев и полноту live state.
  9. Какая публичная аудитория ожидается и сколько одновременных повторов разрешать? Начальные caps выставляются по измерениям, не по размеру RAM в рекламе.
  10. Будут ли реклама, платные функции или другие коммерческие сценарии? Это влияет на допустимость Vercel Hobby и условия использования источников.

12. Основания и актуальность

Локальный первоисточник: v2/research/free-hosting.md, конфигурация Next, страницы и data adapters, FastAPI app/config/hub/replay, refresh/paths/locks/weekend/FastF1 modules, ML predict/simulate/gbm/backtest, retrain gate и Windows schedule scripts. Размеры измерены заново. Build не запускался, код не менялся. Перечень динамических причин получен из кода, а не из нового build output.

Веб-проверка проведена 10.10.2026. Ссылки на официальные документы стоят рядом с утверждениями. Основные исправления прошлой заметки: больше динамических страниц, raw/fastf1 нужен для rebuild, полный retrain-gate не равен одному train, Koyeb free ещё описан официально, Hugging Face compute требует проверки paid-plan eligibility, Neon обновил free storage. Oracle 2 OCPU / 12 ГБ подтверждён текущей официальной документацией; старые 4/24 нельзя использовать для новой бесплатной tenancy.

Некоторые страницы меняются быстрее поискового индекса. Перед созданием ресурсов владелец сверяет план и estimate в dashboard. По Workers cron встречаются расхождения CPU limits; резервный диспетчер выбирается только после проверки актуальной конфигурации. Не проверены выдача Oracle capacity конкретному владельцу, создание аккаунтов, реальные облачные CPU-бенчмарки, нагрузочная ёмкость live и возможность бесплатного DNS-имени. Это контрольные точки rollout, а не выполненные действия.

Единственный созданный артефакт: research/deploy-plan.html. План предусматривает полную независимость от домашнего компьютера после первоначальной выгрузки состояния.
